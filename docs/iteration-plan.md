# Proposed iteration sequence

Estimate: one discovery/decision iteration (I0), six implementation iterations (I1–I6), and one final acceptance/release iteration (I7). This is a planning hypothesis; the real count is whatever the evidence ledger records. Each iteration is a coherent cycle with a frozen scope, acceptance criteria, checks, evidence, and a user validation gate before the next iteration starts.

| Iteration | Scope | Gate |
|---|---|---|
| I0 — Requirements and lifecycle | Trace PDF requirements/rubric to acceptance criteria; define initial API contract, DBMS-vs-domain idempotency, payment/reservation/fulfillment lifecycles, recovery and security boundaries; review the public-safe tree/history | User validates scope and provisional policies; public remote/first push and `main` protection are completed before I1 |
| I1 — Foundation | Initialize app workspaces, local PostgreSQL workflow, migrations, typed config, CI, and API/UI shell | Clean install, lint/typecheck/build, database migration, contract skeleton, and initial required CI checks evidence |
| I2 — Checkout and inventory | Catalog/checkout flow, server-side price calculation, atomic reservation, scoped idempotency, API persistence | PostgreSQL concurrency and duplicate-command gates pass |
| I3 — Payment lifecycle | Provider adapter, durable attempt/event records, webhooks, status lookup, reconciliation, timeout and retry policy | Sandbox or controlled contract evidence; no blind duplicate request under ambiguous outcome |
| I4 — React experience | Responsive checkout, accessible state/error handling, API integration, refresh recovery, approval/decline/pending/unknown states | Browser flow evidence on target mobile and desktop sizes |
| I5 — Reliability and scorecard | Boundary and concurrency tests, coverage threshold, security/error review, accessibility, performance and cross-browser fixes | Measured scorecard with defects resolved or clearly disclosed |
| I6 — Terraform and AWS | Cost-aware Terraform for a single Fargate service and PostgreSQL; configure secrets safely; deploy and smoke-test | Review plan/cost before apply; live endpoint and browser-to-API smoke evidence |
| I7 — Final acceptance and release | Re-run rubric, verify README/setup/evidence, inspect the public history/artifacts, and confirm deployed links | User validates final evidence and handoff; the repository is already public from I0 and has incremental feature history |

I0 outputs are `requirements-traceability.md`, `api-contract.md`, and `payment-lifecycle.md`, together with the approval record in `open-decisions.md`. The user approved the scope and policies on 2026-09-24; the neutral public repository and `main` protection are in place; the I0 feature PR was merged as `c8d3fe0`. I0 is complete. I1 implementation and automated gates were completed on `feat/project-foundation` in PR #3 and merged into `main` on 2026-09-24; local and hosted checks passed. The user then requested an early deployment of the I1 shell; deployment PRs #4–#7 were approved and merged, and the live URL still serves that I1 foundation. This did not implement checkout or payment behavior.

I2 is in progress on `feat/checkout-reservation`, scoped to the API and PostgreSQL catalog/checkout/inventory slice; the React checkout UI remains in I4. The branch adds a seeded catalog, server-priced checkout snapshots, a proposed guest-session cookie scope, atomic inventory holds, 10-minute expiry, and idempotency. It is not deployed. The PostgreSQL integration gate uses independent API connections and a disposable local `_test` database. Demo fee values and PII retention are still open for the I2 review gate. I2 will not merge or begin I3 until the user validates its PR evidence.

Within an iteration, independent analyses can run in parallel when file ownership and contracts are clear. The review artifact is feature-based: normally one integrated PR for a vertical slice, or separate PRs only for independently reviewable features. A PR, commit, agent task, or prompt is not itself an iteration. Publish meaningful branch progress after the public-remote gate, then present the completed PR evidence to the user. Integration, user validation, merge, and the next iteration remain sequential. See `git-workflow.md` for the branch, commit, and PR conventions.
